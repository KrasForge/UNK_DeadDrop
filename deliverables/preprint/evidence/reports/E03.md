## Activation and configuration

The startup activation event can permit extension activity after the initial lure workspace is removed, provided the extension remains installed and enabled. Repository cleanup therefore does not establish removal of the installed component. The source record describes cleanup of workspace task and staging files after installation. Neither the manifest nor cleanup code establishes that a particular user permitted installation. [S1]

Workspace configuration supplies the server URL, client identifier and agent token through the `googleUpdateSupport` namespace. Other keys select the agent archive and Windows activation mode. Empty defaults in the manifest show why the extension alone may be insufficient to reconstruct a deployment's destination. No token values are reproduced.

## Build interpretation

The May agents and a July implant expose different VCS revisions. The macOS arm64 agent records cgo enabled; other examined builds differ. These are build attributes, not a unique identification of a physical machine. VCS timestamps should not be relabeled as certified compilation times. No editor execution, persistence test or fresh external hash lookup was performed. [S1, S2]
